# 0.10.1後の実機報告と次の実装計画

この文書は0.10.1後の調査と合意した計画の記録です。以下の対象は0.11.0で実装し、[更新・実機受け入れ手順](UPGRADE_0.11.0.md)へ進めました。

- 卵の生成位置／素材照合と診断、初期取り込み後の追加モブ検出、現在のUE位置への専用summon。
- UE照明とバニラ風の光の分離、ネイティブの時刻・天候・明るさ・光／遮光を使う光環境、AOと設置・破壊後の伝播。
- ネイティブの地上アイテムモデル、投下・拾得のID付き処理。
- アトラス、隠れた面の除去、近傍衝突、地形ストリーミング、JPEGとWindows GPU共有の選択、映像FPS／遅延の計測。

UE5.8のビルド・描画・Windows GPU相互運用、RTX 5060の1080p・4～6チャンク・実映像30fps以上は未確認です。ソースの実装と実機の受け入れ成功を区別します。モブ固有AI・オフハンド等、前版から残る対応範囲は更新手順に記載します。

以下は調査時点の記録です。「現在」などの記述は0.10.1時点を指します。
基準コミット：c462eb8。ユーザー実機で持ち物モデルの表示成功を確認。
UE5.8はクラウドにないため、UEビルド・描画・統合動作をクラウドで検証済みとは扱いません。

## 現状と調査結果

添付ログは素材検証・シェーダーコンパイル・Play開始・停止を含む。
UEは0.10.0のUDP/TCPリスナーを開始している。モブのテクスチャとマテリアルの検証は記録されているが、Receiverに割り当てたpaletteの内容・テンプレート数・召喚イベントの受信／拒否理由はない。
モブ召喚失敗の原因はこのログだけでは確定できない。

- スポーンエッグ：BridgeMobWorld::SpawnEggは、有効なUE操作・palette・種別からappearanceへのTemplates対応・空いたカプセル領域を必要とする。モデルが存在することだけでは足りない。現在は失敗理由を主にMC statusのlastActionへ返すだけで、UEログから追いにくい。衝突判定はプレイヤーも除外していないため、近い場所での拒否も調べる。
- `/summon`：Minecraftの標準コマンド。UE用コマンドとして実装されていない。MobBridgeは初期取り込みIDが変わった時だけ、現在のMCモブを走査する。その後に召喚されたモブは自動転送されない。既存個体の外見照合はUUIDを中心に行い、新しい個体への種別テンプレート利用もない。
- 添付ログの`ExplosionSystem is unset`は専用爆発Niagaraの未設定であり、モブ召喚失敗の根拠ではない。
- `Bridge dust: missing_surface`は足元のブロック解決失敗。素材未準備と同じではない。バニラ地形・保存済みUE床・輸入境界など、どの床で起きたかを診断へ追加する。

### ライティングONにも変更がある

0.9.0のOFF追加時、撮影のLit/Unlit切り替えを追加した。
0.10.0では白浮き対策として次も変更した。

- ONをFinalToneCurveHDR＋線形FloatRGBA読み戻し＋一度のsRGB変換へ変更。
- OFFをSceneColorHDRへ変更し、同じ撮影からRGBと逆不透明度を取得。
- 配信撮影の時間AA・モーションブラーを停止。
- 撮影時のShowFlagsをLit/Unlitから設定し、光・影・Specular・露出などを切り替える。
- 生成済みの共通マテリアルをSpecular0へ修正。これはON側にも反映される。

従って「OFFの追加はONの見た目に何も影響しない」とは言えない。
撮影経路・反射設定・露出・法線・面の向き・UEの光源設定を分けて調べる。
画像の明暗だけで法線反転や光源向きを断定しない。
手続きメッシュのUE/Lumen対応と陰影品質も、実際のUE設定で調べる。

## 実装順

### 1. モブ生成の復旧と診断

1. 卵の入力、受信、種別、palette割り当て、テンプレート照合、衝突判定、Actor生成、モデル初期化を段階別に記録する。MCにも短い日本語の理由を表示する。
2. UEで読み込まれたpaletteの個体モデル数・種別テンプレート数を確認し、種別不一致、未対応移動、部位データ不正を区別する。
3. 卵の生成位置を面とモブ寸法から決める。衝突を無視した強制生成ではなく、プレイヤー／床／壁それぞれの妨害理由を示す。境界も検査する。
4. `/summon`で追加されたMC個体を初回走査後も検出し、対応する種別テンプレートへ照合する。未知の見た目は必要な素材の再書き出しを案内する。
5. UE操作の現在位置と輸入領域で対象を決め、初回取り込み・卵・追加個体を重複生成しない。生成成功ACKの後にだけ元MC個体の一時停止を行う。停止・切断時の復帰を維持する。

ユーザーが失敗を確認したゾンビ・村人を最初の検証対象にする。実行例は `/summon minecraft:zombie`。両種のスポーンエッグと初期取り込み後のsummon転送を確認する。飛行／水中種や全種固有AIは別の実装であり、召喚復旧と混同しない。
標準`/summon`の座標はMC側である。UE移動後にMCプレイヤーの`~ ~ ~`とUE位置がずれる点を表示・案内し、UE上の座標での召喚が必要なら専用のBridgeコマンドを用意する。

受け入れ：対応種の卵と初回取り込み後のsummonで1体だけ生成し、描画・歩行する。拒否理由が確認でき、MC側も意図せず二重に動かない。

### 2. UEライティングONの正常化

1. 同一の保存済みテストレベルで、6面の法線・三角形の向き・影、DirectionalLightの方向、SkyLight、露出、トーンマッピングを個別に比較する。
2. UE用とバニラ用のマテリアル／描画設定を分ける。バニラのための設定がONの共通素材へ恒久的に混ざる構造を見直す。
3. ONで必要な影・GI・反射を明示し、OFFから戻した時に設定や露出履歴が残らないようにする。古い色の二重変換は戻さない。
4. 手続きメッシュで利用できるUEのライティング機能を実機で確認し、必要なら描画メッシュの生成方法も改める。

受け入れ：6面の照明方向と落ちる影が一致し、ON→OFF→ONで同じ位置の見た目が復元する。ブロック、持ち物、腕、モブの色が一致する。

### 3. OFFをMinecraft風のライティングへ

現OFFはUE光源を止めて素材を明るく見せる方式であり、Minecraftの地形ライティングを再現していない。空の昼夜変化だけでは地形は暗くならない。

実装対象：

- 面の向きによる明るさ。
- ブロックの角ごとのスムーズライティング／AO。
- 空からの明るさと屋内遮蔽、ブロック光源の明るさ・伝播。
- 時刻、天候、ディメンション、MCの明るさ設定等を反映するlightmap相当の処理。
- 腕・持ち物・モブ・ドロップへの周囲光の反映。
- Minecraftの実際の空との色・時間の整合。

初期取り込みではMCの光データを利用する。UE側で設置・破壊するため、その後はUE管理の地形から局所的に光を更新する必要がある。元MC地形の光を毎回読むだけでは、新しく置いた松明や開けた穴の光は正しくならない。
照明モードを変えてもゲーム判定はUEに維持する。OFFではUEの物理的な影を止め、バニラ方式の陰影を描く。通常コマンド`lighting on/off`は維持する。

受け入れ：昼／夜、屋外／屋内、松明の設置／破壊、壁で遮った光、角の陰影をMinecraft単体の同じ素材と比較する。

### 4. アイテムを投げる

設定済みのアイテム投下キーを使う。Minecraft標準の1個／スタック投下操作を尊重する。

- UEで投下位置・初速・重力・地面／壁の衝突を処理する。
- 取得済みのアイテムモデルと、その地上表示用のネイティブ持ち方を利用する。既存の手持ちモデル4種類だけでは地上表示の姿勢は足りない。
- 回転、浮き、個数、拾得、近い同種の合流、寿命を管理する。
- MCインベントリとUEのドロップをID付きの取引で対応させる。再送・生成拒否・切断でアイテムの二重化や紛失を起こさない。
- MC側の標準投下で見えないMCアイテムエンティティだけが増える状態を防ぐ。専用ローカル環境の範囲で処理する。

受け入れ：投下後の所持数、UE個体数、拾った後の所持数が整合し、通信再送でも増減しない。

### 5. フルHD・長い描画距離・30fps以上

描画負荷と映像転送負荷は別に計測する。MC表示FPS、UEレンダーFPS、受信／表示したUE映像FPSを分ける。
目標はRTX 5060で1920×1080の実映像30fps以上、描画距離4～6チャンク。まず4チャンクで測定し、6チャンクへ伸ばす。1チャンクは16ブロックなので、距離の目安は64～96ブロック。実際の読み込み領域はMCのチャンク配置に合わせて定義する。
30fpsの1フレーム予算は33.3msだが、遅延は別に入力から表示まで測定する。

まず計測：UEゲーム／レンダー／GPU、描画面数・draw call・マテリアル数・影、GPU読み戻し、圧縮、TCP待ち、復号、MC upload、実映像FPSと遅延分布。

地形描画：

- 現在は8ブロックセル内で素材ごとに面をまとめる方式。隠れた面も生成し、セル／テクスチャごとの描画が増える。
- 隣接ブロックで見えない面を除去し、チャンクの可視面をまとめる。
- 形状・光・UVが一致する面を結合する。スラブや階段などをフルブロック扱いにせず、モデル形状と遮蔽情報を保持する。
- テクスチャ集約とマテリアル数削減。光の境界と繰り返しUVを守る。
- UE位置に追従する地形ストリーミング、必要なMCチャンクの取得、編集箇所だけの非同期再構築を設計する。遠方描画と近傍の衝突／選択形状を分ける。
- 8ブロックセルの半径設定を増やすだけではMCのチャンク距離にはならない。現在の静的輸入範囲・境界・転送上限も変更が必要。

映像転送：

- JPEGを比較用・互換用として残す。
- 同じWindows/GPUでUEのDirectX出力をMCの描画APIへ共有する試作を優先する。共有可能なリソース、同期、MC側のネイティブモジュール、GPU／ドライバーの対応を調べる。
- DX→OpenGL等の相互運用はGPU依存であり、普通のJavaテクスチャにそのまま渡せるとは扱わない。
- 色・アルファ・フレームの所有権を定義し、RGBと空マスクを同一フレームで共有する。遅い表示側へ古いフレームを蓄積しない。
- GPU共有が成立しない環境ではハードウェア圧縮等を比較する。低解像度への変更だけでフルHD達成としない。
- UEをゲームとして起動し、Editorのビューポートとの重複描画を避ける運用も測定する。

受け入れ：指定GPU・距離・同一シーンで、昼夜／光源／モブ／アイテム投下を含め1920×1080の実映像30fps以上と遅延分布を確認する。瞬間的なMCのFPS表示だけで達成とは言わない。

## 残る情報と変更範囲

確認済み：失敗対象はゾンビ・村人、コマンドは `/summon minecraft:zombie` 等。GPUはRTX 5060、希望描画距離は4～6チャンク。卵失敗直後の `/uebridge status`（操作理由と卵テンプレート数）があると生成拒否をさらに絞れる。
現時点で原因未確定のモブ生成・陰影を修正済みとは扱わない。
既存のレベル、Content/Config/Saved、ローカル素材・スキンを保持する。既存サーバーや他プロジェクトへ適用しない。
