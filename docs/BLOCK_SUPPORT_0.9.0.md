# 0.9.0 ブロックの対応範囲とローカル素材

0.9.0 はブロックを衝突用の箱として描く方式から、Minecraft の実際のブロックモデルとブロック状態を使う方式へ拡張します。画像・リソースパックのデータは使用する PC で書き出して取り込みます。配布 ZIP に Minecraft の画像は含みません。

## 必須の素材更新

旧版の素材パレットには任意形状と各状態の衝突形状がありません。MOD と UE ソースを更新して UE をビルドした後、Minecraft でローカルワールドを開き `/uebridge textures export` を実行してください。書き出しの完了後に、更新した UE Python の取り込みスクリプトを使用します。`setup_minecraft_visuals("C:/UEBridgeTest/MC-Test")` からも最新の素材を取り込めます。UE の Play は停止し、レベルを保存し、BridgeReceiver を 1 個配置します。

`manifest.json` は version 2 です。取り込む内容は次のとおりです。

- ブロック状態の variants / multipart と、親モデルを解決した各モデルの要素・面。
- 各面の UV、UV の回転、要素の回転、モデルの方向、uvlock、色付きの面、透明度。
- 各ブロック状態の Minecraft ネイティブの衝突形状と選択形状。見た目の形状とは別に保持します。
- 粒子用のテクスチャ、バイオームから採った色、植物などの位置ずれの情報。
- 除外された ID と、その理由を記録した `excluded` 一覧。

通常のフルブロックでは衝突形状と選択形状が同じなので、同じ不可視の箱を共有します。不可視の箱はブロックの色や ID によらず衝突応答ごとにまとめますが、命中した各インスタンスの ID・状態・元の座標を別に保持します。バイオームによって草や葉の色が変わる場合にも対応し、8×8×8 のセルあたり 512 色・2,048 組、8,192 行、転送全体で 524,288 行を上限にしています。描画面は画像・色付きかどうか・実際に必要な色でまとめます。

## 今回の通常ブロック

フルブロック、階段、ハーフブロック、柵、塀、板ガラス、鉄格子、植物、ボタン、レバー、トラップドア、ドアなど、専用描画を必要としないバニラのブロックモデルを扱います。通常のアイテム全種類の描画対応は今回の対象に含みません。

初期転送では、設置済みのブロックの状態をそのまま使います。たとえば階段の向きと角、上下のハーフブロック、柵の接続、開いたドア、ボタンの壁・床・天井への取り付けを区別します。Minecraft の衝突形状で歩行し、選択形状で狙います。草のように衝突しないブロックも狙って破壊できます。

UE 側での新規設置では、向き、設置面、クリックした高さから軸・方向・上下を決めます。ハーフブロックの結合、階段の内角・外角、柵・塀・板ガラスの接続、ドアなどの 2 段ブロックの設置・破壊も更新します。木製ドア・トラップドア・フェンスゲートは右クリックで開閉し、ボタンとレバーは表示状態を切り替えます。石系のボタンは 1 秒、木製ボタンは 1.5 秒で戻ります。

ツタ・ヒカリゴケ・スカルクヴェイン・樹脂の塊の新規設置は、クリックした面への1方向の取り付けを扱います。既存の同じ植物への面追加や、植物ごとの支持ブロックの適否判定は未実装です。

これはすべての Minecraft システムの移植を意味しません。レッドストーンの伝播、作物の成長、ランダム tick、砂・砂利の落下、燃焼、インベントリ画面、乗り物などの独立したゲームシステムは実装していません。表示・衝突・設置に対応した ID でも、こうした個別の動作が必要な場合があります。

## 今回の除外

`BlockGeometryCapture.exclusion()` が実際のバニラ登録ブロックを判定します。Minecraft の `BlockState.hasBlockEntity()` が true のブロック、`BlockRenderType.MODEL` 以外のブロック、空気、MOD が追加したブロックは今回の転送から除外します。

- 看板類：通常の看板、壁の看板、吊り看板、壁の吊り看板。
- 流体：水、溶岩、気泡柱。水没した通常ブロックの固体部分は扱いますが、水は描画しません。新規設置では `waterlogged=false` にします。
- ブロックエンティティを持つもの：チェスト・銅のチェスト、シュルカーボックス、かまど、ホッパー、ベッド、旗、頭・スカル、棚、焚き火、ポット、ビーコン、エンチャントテーブル、コマンドブロック等。登録状態により判定し、実際の全 ID は書き出した `excluded` に残します。
- 明示的な特殊 ID：`nether_portal`、`end_portal`、`end_gateway`、`fire`、`soul_fire`、`piston`、`sticky_piston`、`piston_head`、`moving_piston`、`redstone_wire`、`tripwire`、`tripwire_hook`、`structure_void`、`light`、`barrier`、`bubble_column`。名前空間はすべて `minecraft:` です。

任意のリソースパックがモデルや画像を欠落させたり、書き出しの上限を超えたりした場合も、該当する ID と理由を `excluded` に記録します。存在しないモデルをフルブロックに置き換えて対応済みとして扱いません。UE は初期転送した状態のモデル・素材が欠けていると、そのセルを確定せず、`blockModelError` に対象を報告します。

## 検証の範囲

クラウドのローカル Minecraft 1.21.11 クライアント JAR を使い、`python3 tools/test_block_resources.py` で実際のモデル資源を検証できます。画像と書き出しファイルは一時ディレクトリ内で検証後に削除されます。

資源の検証結果は 1,168 個のブロック状態ファイルから 1,008 個の静的モデルの ID、2,055 個の親解決済みモデル、1,075 個の画像でした。160 個は専用描画・不可視のため面がありません。この数は画像とモデルの解決結果です。前述のブロックエンティティや特殊 ID を取り除いた、ゲーム側の最終対応数とは異なります。書き出した `manifest.json` の `blocks` と `excluded` が、その PC のリソースパックを含む実際の一覧です。

UE の Automation Test にモデルの回転、UV、multipart、ネイティブ形状、植物の位置ずれの確認を追加しています。クラウドには UE がないため、UE ビルド・材質コンパイル・実機描画を確認済みとは扱いません。
